## 2. Tool-selection discussion

The user asked which tools should be used to produce a high-rigor, high-design engineering framework.

The recommended workflow was deliberately multi-tool rather than relying on one application:

```text
MindMap AI
  -> Mermaid / Graphviz
  -> LaTeX / TikZ
  -> FigJam
  -> Figma
  -> Canva
  -> GitHub
```

### Roles of the tools

- **MindMap AI:** maintain ontology, stage hierarchy, roles, questions and core objects.
- **Mermaid / Graphviz:** validate directed logic and produce reproducible graph sources.
- **LaTeX / TikZ:** formal mathematical notation and publication-grade figures.
- **FigJam:** systems-architecture exploration, interfaces and feedback relationships.
- **Figma:** final deterministic vector master.
- **Canva:** presentation and animation derivatives.
- **Python:** structural/computational validation.
- **GitHub:** durable authority, source control and provenance.

Figma was selected as the central visual production environment, with TikZ as the publication authority and Mermaid/Graphviz as the logical authority.

## 5. Audit of the first generated image

The user explicitly asked whether the image had preserved the canonical framework exactly.

The answer was **no**.

### Preserved correctly

- seven stage names;
- stage order;
- broad resilience-to-sustainability logic;
- Stage 6 transformation concept.

### Non-canonical additions detected

- "Downstream Thesis Outputs and Applications";
- SDG panel;
- critical interfaces / recovery bottlenecks and other added outputs;
- `S_T,S_O,S_E,S_P` variables;
- extra application examples;
- reformulated equations and labels.

The image was therefore reclassified as **illustrative**, not authoritative.

This led to the frozen design rule:

```math
\boxed{\textbf{CHANGE THE VISUAL HIERARCHY, NOT THE SCIENTIFIC CONTENT.}}
```

No new SDGs, equations, variables, applications, outputs, labels, or interpretations may be inserted into a canonical representation without explicit approval.

## 11. State-space notation question: X1, X2 versus Y1, Y2

The user proposed that `X_1` and `X_2` were merely generic coordinates used to draw the viability concept, but noted a rigor problem: the canonical framework uses `Y` as the system-state object.

The user proposed replacing:

```math
X_1,X_2
```

with:

```math
\boxed{Y_1,Y_2}
```

and interpreting them as a two-dimensional projection:

```math
Y(t)\in\mathbb R^n
\xrightarrow{\text{2-D projection}}
(Y_1,Y_2).
```

This correction was approved.

### Rationale

- `Y` is already the canonical system-state object.
- Introducing `X` creates a competing notation with no need.
- The two-dimensional viability plot is an illustrative projection, not a definition of the physical state variables.
- `Y_1` and `Y_2` should remain generic until the mathematical model formally assigns physical meanings.

### Thesis-safe caption

> **`Y_1,Y_2`: illustrative coordinates of a two-dimensional projection of the coupled system state `Y`.**

A stricter alternative is to remove coordinate labels entirely and show only `K`, `V`, and the trajectory.
